# PRISM 升级路线图

> 文档状态：规划稿
> 更新时间：2026-09-03
> 适用版本：PRISM 当前 `main` 分支

## 1. 升级目标

PRISM 已经具备“资料导入 → 知识图谱 → 个人模型 → 人生分支 → 深度推演 → 多宇宙对比 → 圆桌审计”的端到端能力。下一阶段的重点不是继续堆叠 Agent，而是把它从一条技术管线升级为：

> **可信、可解释、可回访、可执行的个人决策工作台。**

用户最终应该能够：

1. 用很少的前置学习成本提出一个真实问题。
2. 明确知道系统使用了哪些资料、哪些是事实、哪些是推断。
3. 比较不同选择的代价、约束和不确定性，而不是只看一个分数。
4. 将分析结果转成现实中的短期实验，并在复盘后更新模型。
5. 随时暂停、取消、重试、导出或删除自己的数据。

### 1.1 非目标

- 不把 PRISM 包装成预言、诊断或专业咨询工具。
- 不把文学作品分析混入个人画像、关系人和人生推演。
- 在核心用户闭环稳定前，不优先开发社交广场、复杂社区和大量新 Agent。
- 在明确多用户需求前，不为了技术时髦直接拆成微服务。

## 2. 当前基线与主要缺口

### 2.1 已有基础

- Vue 3 + Vite 前端，Flask REST API 后端。
- 支持多种文档、表格、聊天记录和图片资料导入。
- 支持个人画像模式与显式虚构的文学分析模式隔离。
- 已有证据引用、来源校验、事实门槛、防漂移、真实性账本和圆桌结构校验。
- 已有任务持久化、取消、过期回收、幂等和原子存储能力。
- 已有中英文界面、图谱观察台、分支、推演、对比和圆桌导出能力。
- 当前后端测试为 140 项通过，前端生产构建通过。

### 2.2 需要优先解决的问题

| 领域 | 当前风险 | 升级方向 |
| --- | --- | --- |
| 首次体验 | 用户需要理解图谱、模型、分支等内部概念 | 以“决策问题”作为入口，流程由系统引导 |
| 可解释性 | 后端已有证据索引，但用户不一定能在界面上看懂证据链 | 结论、原文、来源、置信度和推断类型联动展示 |
| 任务体验 | 主要依赖后台线程和前端轮询 | 统一任务中心，支持实时进度、取消、重试和恢复 |
| 持久化 | 本地 JSON 适合单机，但不适合多实例和并发用户 | 先抽象存储接口，再按部署形态迁移 SQLite/PostgreSQL |
| 安全 | 当前存在开放 CORS、默认密钥和无用户权限边界 | 公开部署前完成认证、授权、密钥和日志治理 |
| 隐私 | 日记、聊天记录等资料可能进入 Zep Cloud | 明示同意、数据生命周期、导出、删除和脱敏 |
| 结果闭环 | 目前重点是生成分析，缺少行动与复盘 | 增加 7/30/90 天实验、复盘和模型版本更新 |
| 质量 | CI 主要覆盖单一 Python 版本，缺少真实浏览器 E2E 和 LLM 评测 | 建立版本矩阵、契约测试、E2E 和可重复评测集 |
| 文档 | README 中测试数量、Python 支持范围可能落后于实际状态 | 每次发布同步版本、测试数和兼容性说明 |

## 3. 产品原则

1. **证据优先**：没有证据时明确标注未知，不用流畅语言掩盖缺口。
2. **用户掌控**：用户决定资料范围、参与者、推演深度、是否保存和是否更新模型。
3. **过程可见**：长任务显示当前阶段、预计等待、可执行操作和失败原因。
4. **不确定性诚实**：同时展示支持证据、反证、敏感变量和结论适用范围。
5. **增量使用**：用户可以先得到一个小结果，再逐步补充资料和深度。
6. **模式隔离**：个人模式与文学模式在数据、导航、提示词和输出语义上保持边界。
7. **本地优先思维**：敏感资料最小化上传，能本地处理的内容不经过大模型。

## 4. 目标用户路径

### 4.1 个人决策路径

```text
提出决策问题
  -> 设定时间范围、目标和不可妥协条件
  -> 预览并选择资料
  -> 查看事实与资料缺口
  -> 生成个人模型
  -> 生成并比较人生分支
  -> 选择一个或多个分支进行深度推演
  -> 圆桌质询与证据审计
  -> 生成现实行动实验
  -> 复盘并决定是否更新模型
```

### 4.2 文学分析路径

```text
选择文学分析模式
  -> 导入作品或粘贴文本
  -> 查看章节、人物、主题和证据引用
  -> 运行指定的文学问题分析
  -> 导出分析报告
```

文学路径不得出现个人分支、关系人 Agent、人生推演或个人预测入口。

### 4.3 回访用户路径

- 首页显示最近项目、未完成任务、最近一次模型版本和下一步建议。
- 用户可以从任意中断点继续，而不是重新走完整流程。
- 补充资料后先显示变更预览，再由用户确认是否重新合成。
- 历史结果保持可读，新的模型版本不覆盖旧结论。

## 5. 用户体验升级

### 5.1 P0：首次成功体验

- 新建项目向导：名称、模式、决策问题、时间范围、目标和约束。
- 资料导入预览：文件类型、大小、可提取文本片段、敏感资料提醒和去重提示。
- 统一任务中心：图谱构建、画像合成、关系人生成、分支生成和圆桌任务使用同一套状态展示。
- 任务状态统一为 `待处理 / 进行中 / 可继续 / 已完成 / 失败 / 已取消 / 已过期`。
- 每个失败状态提供“查看原因、重试、取消、回到上一步”四种明确操作。
- 首次使用提供脱敏的虚构演示项目，避免用户必须先提交真实隐私资料。

**验收标准**

- 新用户无需阅读技术文档即可完成第一次分析。
- 任意长任务都能看到当前阶段、进度、最近更新时间和下一步操作。
- 刷新页面或重启后，可以恢复查看任务最终状态。

### 5.2 P1：工作台与证据体验

- Workbench 作为项目中心，显示项目健康度、模型版本、资料缺口和下一步建议。
- 结论卡片统一显示：结论、证据类型、原文引用、来源资料、时间、置信度和适用范围。
- 增加证据抽屉：从画像字段、分支假设、推演事件和圆桌审计结果反向定位原始资料。
- 明确区分“已观察事实”“基于多条事实的推断”“尚未验证的假设”。
- 重要结论支持用户纠正、标记不准确和要求重新分析。

**验收标准**

- 用户可以从每条重要结论回到至少一个来源或明确的“证据不足”说明。
- 任何无法引用来源的内容都不会显示为确定事实。
- 用户纠正不会静默覆盖旧模型，而是形成可追踪的新版本。

### 5.3 P1：分支、推演与圆桌

- 分支卡片展示目标、代价、前置条件、风险、证据缺口和反转变量。
- 对比页从单一适配分数升级为现金流、时间、关系、健康、心理压力和不确定性的权衡矩阵。
- 推演页显示阶段时间线、真实性账本、触发的熔断原因和可选择的下一步。
- 圆桌支持逐条显示发言、暂停、取消、重试、参与者筛选和结束后重新质询。
- 主持人结论必须同时展示收敛证据、分歧证据、开放问题和证据等级。
- 导出 Markdown 后增加可选 PDF/HTML 报告，包含模型版本和资料范围。

### 5.4 P2：行动与复盘

- 将圆桌和对比结论转换为 7/30/90 天实验，而不是直接给出不可验证的宏大建议。
- 每个实验包含：目标、最小行动、成功指标、停止条件、预计代价和复盘日期。
- 复盘时记录现实结果与模拟差异，标注“模型错误、资料缺失、外部变化或执行偏差”。
- 用户明确同意后，才将复盘内容纳入下一版个人模型。

### 5.5 通用体验质量

- 支持键盘完整操作、可见焦点、语义化标签、错误文本和足够的颜色对比度。
- 移动端保证表格、图谱、圆桌 transcript 和长文本不会横向溢出或互相遮挡。
- 所有用户可见文本进入 i18n；错误信息、进度信息和导出文件名也保持中英文一致。
- 统一空状态、加载状态、网络断开、权限不足和过期任务的视觉语言。

## 6. 功能完整性

### 6.1 项目与资料生命周期

- 项目草稿、归档、恢复和彻底删除。
- 资料清单、资料类型、上传时间、内容哈希、处理状态和关联模型版本。
- 补充资料前提供影响预览：哪些字段、关系、分支和结论可能变化。
- 一键导出项目元数据、个人模型、证据索引和用户创建的行动计划。
- 提供备份包导入，保证单机用户可迁移环境。

### 6.2 决策模板

首批模板建议限定为四类：职业、学习、关系、创作。模板只负责收集问题和指标，不替用户预设结论。后续可增加自定义模板。

### 6.3 文学模式

- 章节结构、人物关系、主题、叙事视角和关键段落引用。
- 支持“只分析当前作品”和“跨作品比较”两种明确范围。
- 所有文学结论标注引用章节或文本片段。
- 禁止把文学人物当作用户关系人，也禁止从作品推断用户人格。

## 7. 技术架构路线

### 7.1 存储演进

采用渐进迁移，不一次性重写所有模型：

```text
现阶段 JSON 文件
  -> Repository 接口与 schema 版本
  -> SQLite（单机/小规模部署）
  -> PostgreSQL + 对象存储（多用户生产部署）
```

- 文件内容和结构化元数据分离。
- 所有记录包含 `created_at`、`updated_at`、`schema_version` 和来源版本。
- 迁移脚本必须可重复执行、可回滚并在备份副本上验证。

### 7.2 任务与实时事件

- 将进程内 `threading.Thread` 逐步迁移到 RQ、Celery 或同等任务队列。
- 统一任务接口：创建、查询、取消、重试、恢复、幂等键和错误码。
- 前端优先采用 SSE 接收进度和 transcript 事件，轮询作为降级方案。
- 任务日志只保存结构化阶段信息，不保存原始隐私资料。

### 7.3 API 契约

- 引入 `/api/v1` 版本前缀。
- 使用 Pydantic/OpenAPI 定义请求、响应和错误结构。
- 统一错误格式：`code`、`message`、`details`、`retryable` 和 `request_id`。
- 列表接口支持分页、排序和稳定的更新时间字段。
- 对创建类接口支持 `Idempotency-Key`，防止重复生成和重复扣费。

### 7.4 LLM 与 Zep 网关

- 用统一 Gateway 封装模型选择、超时、重试、限流、缓存和供应商降级。
- 每次调用记录模型版本、Prompt 版本、Token 用量、耗时、失败原因和估算成本。
- 在长任务开始前估算时间和成本，允许用户选择“快速/标准/高质量”档位。
- 失败时优先保留已有中间结果，不因最后一步失败而丢失整个任务。
- Zep 同步增加状态、重试、断线恢复和本地可读的同步摘要。

## 8. 安全、隐私与可信使用

公开部署前必须完成以下事项：

- 登录、项目所有权和最小权限控制。
- CORS 从开放通配符改为配置白名单。
- 生产环境禁止默认 `SECRET_KEY`，缺少密钥时拒绝启动。
- 上传文件执行扩展名、MIME、大小、压缩包和路径安全检查。
- 日志、错误追踪和任务详情中不记录原始日记、聊天正文或 API Key。
- 提供资料保留期限、删除、导出和云端处理同意设置。
- 对发送到 Zep Cloud 或 LLM 供应商的资料显示范围、目的和供应商信息。
- 所有结果持续显示“模拟而非预测、诊断或专业建议”的语义边界。
- 财务、健康、法律等高风险主题增加适用范围、人工核验和专业求助提示。
- 记录用户查看、纠正、导出、删除和模型更新等关键审计事件。

## 9. 质量与评测体系

### 9.1 自动化测试

- 后端：Python 3.11、3.12、3.13 兼容性矩阵；若 3.13 存在依赖限制，明确写入支持范围。
- 前端：Node 18、20、22 构建矩阵。
- API 契约测试：使用 fake LLM 和 fake Zep，不依赖真实 API Key。
- 浏览器 E2E：新建项目、导入资料、任务取消、失败重试、文学模式隔离、导出报告。
- 并发和恢复测试：重复请求、进程重启、过期任务、文件锁和数据库迁移。

### 9.2 LLM 结果评测

建立固定脱敏数据集和 golden cases，至少评估：

- 证据覆盖率与引用准确率
- 事实/推断分类准确率
- 个人模型前后一致性
- 关系人事实门槛与防漂移
- 现实账本约束是否被违反
- 文学模式与个人模式是否串线
- 输出延迟、Token 成本和失败重试率

### 9.3 CI/CD 与发布

- CI 必须执行后端测试、前端构建、静态检查和依赖安全扫描。
- Docker 镜像使用不可变版本标签，保留上一版本用于回滚。
- 发布前自动生成变更摘要、数据库迁移清单和兼容性说明。
- 生产部署提供 readiness/liveness、备份校验和恢复演练。

## 10. 分阶段交付计划

以下时间按单人全职开发估算，实际以每阶段验收结果为准。

### P0：产品契约与首次成功（约 1 周）

- [ ] 确认个人模式、文学模式和决策问题的数据契约。
- [ ] 完成新建项目向导和资料导入预览。
- [ ] 统一任务状态、错误码和前端任务中心。
- [ ] 增加脱敏虚构演示项目。
- [ ] 更新 README 的版本、测试数和 Python 兼容性说明。

**完成标准**：新用户可以在不接触技术术语的情况下完成一次可解释的演示分析。

### P1：Workbench 与证据链（约 2-3 周）

- [ ] Workbench 展示项目状态、资料缺口、模型版本和下一步。
- [ ] 结论卡片接入证据抽屉和来源跳转。
- [ ] 分支和对比页改为代价/约束矩阵。
- [ ] 圆桌增加实时进度、暂停、重试和证据审计展示。
- [ ] 补齐移动端、键盘和错误状态。

**完成标准**：用户能回答“这个结论从哪里来、我还能质疑什么、下一步做什么”。

### P2：行动闭环与隐私（约 2-4 周）

- [ ] 增加 7/30/90 天行动实验和复盘。
- [ ] 增加模型版本差异和用户确认流程。
- [ ] 增加导出、删除、保留期限和云端处理同意。
- [ ] 增加日志脱敏和风险主题提示。

**完成标准**：一次分析可以转成现实行动，用户可以安全地撤回资料和结果。

### P3：多用户生产基础（约 3-6 周）

- [ ] Repository 接口与 schema 版本。
- [ ] SQLite 迁移和备份恢复。
- [ ] 认证、项目权限和 CORS 白名单。
- [ ] 任务队列、SSE、幂等键和跨进程锁。
- [ ] API v1、OpenAPI 和统一错误结构。

**完成标准**：服务重启、并发访问和任务失败不会造成数据丢失或状态错乱。

### P4：评测、发布与扩展（持续）

- [ ] Playwright E2E 和 LLM golden set。
- [ ] Token、延迟、错误率和用户反馈监控。
- [ ] Python/Node 版本矩阵和依赖安全扫描。
- [ ] Docker 发布、回滚和恢复演练。
- [ ] 在核心指标稳定后，再评估模板市场、团队协作或分享能力。

## 11. 核心指标与发布门槛

### 用户指标

- 首次得到带证据的有效结果：目标不超过 10 分钟。
- 中断任务恢复成功率：目标不低于 99%。
- 用户能定位来源的结论比例：目标不低于 95%。
- 关键任务取消后不再被后台重新激活：100%。
- 文学模式产生个人推演入口：0 次。

### 工程指标

- 后端单元、契约、E2E 测试全部通过。
- 生产错误必须带 `request_id`，且日志不含敏感正文。
- 数据库迁移和备份恢复至少各完成一次自动化演练。
- 任何外部 LLM/Zep 故障都能给出可理解的错误、重试或降级路径。

### 发布门槛

1. **内部试用**：P0 完成，使用虚构或脱敏数据。
2. **小范围 Beta**：P1、P2 完成，隐私和删除流程可验证。
3. **公开部署**：P3 完成，认证、备份、监控和回滚已演练。
4. **规模化扩展**：P4 指标稳定后再增加协作和商业化功能。

## 12. 建议的执行顺序

1. 先做新用户向导、统一任务状态和证据抽屉，缩短“第一次成功”路径。
2. 再做行动实验和复盘，让结果形成可持续价值。
3. 接着做认证、隐私和任务队列，满足公开部署的安全底线。
4. 最后扩展数据库、实时协议、评测和团队能力。

每个阶段都应先完成验收标准，再进入下一阶段；不要在核心闭环未稳定时继续扩大 Agent 数量或 UI 复杂度。
